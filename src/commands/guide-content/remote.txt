UKP Remote quickstart

Goal: expose registered Services from one machine and consume them from another with the same endpoint commands: search, read, nav, rg, and propose when declared.

Current model:
- The ssh:// path needs nothing running on the host: each invocation wakes a loopback door over the SSH connection (it serves the host Registry fresh and self-reaps when idle). Host prerequisites: the host is ssh reachable and has ukp installed the usual way (npm i -g or bun add -g - the wake finds the standard locations).
- The https path (LAN, public IP, or behind a reverse proxy) uses a resident door: run ukp serve under your process manager. Arbitrary consumers have no SSH credentials, so the listener itself is the trust boundary (TLS + bearer token).
- Prefer host door mode when the whole Registry is safe to declare: run ukp serve without --endpoint to expose every local endpoint behind one port. A Registry that mixes in endpoints you do not want to expose uses --select instead: ukp serve --select a,b,c keeps one port and one door for exactly the named endpoints - everything unselected is not served, routed, or declared (probing its name behaves exactly like probing one that never existed). Reserve per-endpoint --endpoint <name> doors for exposing a single endpoint to different consumers.
- The door reads the host Registry fresh on each request, so newly registered local endpoints appear without restarting the door.
- Declared endpoint names come from the host Service Manifest or discovery document; your registry binds each one under a local handle - the declared name by default, or --name <handle> when that name is already taken (two hosts both declaring 'notes' become your 'notes' and 'ali-notes'). --endpoint during register stays an expected-name assertion on the declared name.

Owner path over SSH (zero ceremony - nothing to start on the host):
1. Prerequisites (once): the host accepts your SSH key and has ukp installed the usual way
   ssh <host> ukp --help
   Peek at the door before importing: ssh <host> ukp list shows the endpoint
   names and capabilities the host declares

2. On the consuming machine, import the door (the first call wakes it)
   ukp register --url ssh://<host>

3. Use the imported endpoints by name; later calls reuse the warmed connection
   ukp list
   ukp read --endpoint <name> notes/x.md
   ukp rg "keyword" --endpoint <name>

LAN HTTPS path:
1. On the host machine, run a tokened TLS door (keep it under your process manager)
   UKP_SERVE_TOKEN=<token> ukp serve --host 0.0.0.0 --tls
   NAT/EIP cloud host (public IP on no NIC)? Name the public IP explicitly:
   UKP_SERVE_TOKEN=<token> ukp serve --host 0.0.0.0 --tls --tls-san <public-ip>
   Linux hosts can go resident-free too: systemd socket activation holds the
   port and spawns the door per use (ukp serve --systemd-socket, recipe in
   the deployment handbook)

2. On the consuming machine, import either the whole door or one endpoint
   ukp register --url https://<ip>:8570 --token <token>
   ukp register --url https://<ip>:8570 --endpoint <name> --token <token>

3. Use the imported endpoint normally
   ukp nav --endpoint <name>
   ukp read --endpoint <name> notes/x.md
   ukp rg "keyword" --endpoint <name>

Scoped keys for a second machine or an agent (instead of sharing the env token):
1. Cold start, once per machine: arm the gate with a bootstrap key whose
   label is NOT a person (an empty token file serves nothing), run WITHOUT
   UKP_SERVE_TOKEN set (while the env token is set the key file is not
   consulted), then start the door and keep it under your process manager
   ukp serve token add gate "notes:ro"         # arming key; raw key ONCE
   ukp serve --host 0.0.0.0 --tls --select notes
   (the arming key is a bootstrap credential, not anyone's daily access:
   arm once with a tool label like 'gate' - minting 'liku' here AND
   sharing to 'liku' later leaves two active keys under one label. Once
   per-person keys exist through share,
   revoke it ('ukp serve token revoke gate'); re-minting on the door
   machine re-arms the gate anytime, so revoking costs nothing. Wanting
   your OWN remote access is just another handover: share to a label
   for your device.)
2. Hand an endpoint over in one gesture (--at is the origin the consumer
   will use, and share probes the door through it)
   ukp serve status [--port <n>]                # door width at a glance
   ukp serve share notes --to liku --at https://192.168.1.10:8570
   share validates 'notes' is on the live roster (a name hidden by --select
   is refused with the wider --select set to merge into the door's own
   start command - restart required, that is by design; share never
   reconstructs the full start line), mints a key scoped to exactly 'notes'
   (add --rw for the propose route), and prints the consumer's paste-ready
   'ukp register --url .../notes --token <key>' line with the raw key shown
   ONCE.
   The keys land in ~/.ukp/tokens (0600, hash-only); scopes are name:ro|rw,
   comma-separated (full power is the explicit '*:rw'); several keys may share
   a label for zero-downtime rotation, and 'token revoke <label>' removes
   every key under that label. Manual form for broader scopes is the
   same mint command, e.g. ukp serve token add liku "notes:ro,cad:rw".

3. On the consuming machine, register with the raw key as the token
   (the share gesture above prints this exact line, scoped to one endpoint)
   ukp register --url https://<ip>:8570 --token <raw-key>
   With an OS credential store present the raw key goes there (Windows
   DPAPI / macOS Keychain / Linux secret-tool) and the registry keeps only
   a token_ref pointer; otherwise it lands in ~/.ukp/registry.toml in
   plaintext (a crash-safety .bak copy can persist beside it). The
   register output names which form landed - treat plaintext files as
   secrets; UKP_ENDPOINT_<NAME>_TOKEN overrides at call time.
   A scoped key only sees its own endpoints: a name the door declares but
   your key cannot touch answers 'no route under your key' (a read-only
   scope has no propose route); names the door does not declare answer
   exactly like nonexistent ones. You do NOT have to hit that wall blind:
   registering with the key already tells you - imports outside your key's
   scope are marked on the spot ("your key has no scope for it") and
   'ukp list' keeps flagging them, because the door's public document
   answers the authenticated fetch with the key's own admitted names.

4. Revoke on the host (effective on the next request - no restart)
   ukp serve token list
   ukp serve token revoke liku

Single endpoint mode:
Use this when you deliberately want to expose only one endpoint instead of the whole host Registry.
   UKP_SERVE_TOKEN=<token> ukp serve --endpoint <name> --host 0.0.0.0 --tls
   ukp register --url https://<ip>:8570 --endpoint <name> --token <token>

Name and identity:
- register --url fetches /.well-known/ukp.json and registers the declared name under a local handle (--name <handle> chooses another, e.g. when the name is taken). That document is public - curl it before registering to preview the endpoint names and capabilities the door declares (self-signed doors: curl -k).
- --endpoint <name> on register asserts the expected name; if discovery declares a different name, registration fails.
- A host door can import everything, --select a comma-separated subset, or --endpoint exactly one endpoint.
- Self-signed HTTPS certificates are pinned on first registration; compare the pinned fingerprint with the serve banner on untrusted networks.
- --tls names the host's interface IPs only. A NAT/EIP host's public IP needs --tls-san <public-ip>; without it registration fails on certificate name mismatch. Adding it later re-signs the persisted cert over the same key, so existing pins survive.
- Non-loopback plain http is refused at both ends: registration refuses the url, and serve refuses to start the door (bearer keys must not travel unencrypted). Use https, ssh://, or loopback http for local testing; --allow-http is the explicit opt-in for a door whose TLS is terminated by a fronting component on another host (reverse proxy, container sidecar) - that hop stays plaintext, and consumers register the edge's https origin, never this door's.
- ssh:// urls take no port: registration rejects one (the woken door listens on a client-chosen loopback port; use an ssh config Host alias for a non-standard sshd port).

Operational note:
- ssh:// hosts: nothing to manage - ukp wakes and reaps doors itself (on Windows, enabling the built-in OpenSSH Server feature once is the low-burden path). SSH lockdown (login-shell restriction, why a forced authorized_keys command= does not compose) and nvm-style install layouts are deployment-handbook material.
- https hosts: keep ukp serve under your normal process manager, for example systemd, Task Scheduler, or a terminal multiplexer. Linux can go resident-free (systemd socket activation, deployment handbook); Windows has no systemd equivalent, so a resident door wants a real service wrapper (WinSW-class) - prefer the ssh:// path there unless consumers have no SSH credentials. The CLI does not install or autostart the door; on Windows, ukp serve --print-task prints the resident-door artifacts (start script, hidden launcher, Task Scheduler command, firewall rule) for you to review and apply yourself - the token stays yours to paste, never printed.
- The deployment handbook is where those recipes live: it ships with this package (docs/remote-deployment.md) and online (https://github.com/CatheadOwl/ukp/blob/main/docs/remote-deployment.md) - Windows resident door (certificate, start script, Task Scheduler), systemd socket-activation units, Caddy, Tailscale, hardening notes.
- serve accepts --max-idle <seconds> to self-exit after that long without requests (the same backstop the woken doors use).

Remember:
- Local registration makes a folder addressable on the host.
- Remote registration imports host-discovered endpoint bindings into the consumer Registry.
- Client Config still stores endpoint names only; after remote import, guide client works the same way as local endpoints.
